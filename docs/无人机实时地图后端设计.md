# 无人机实时地图后端设计

> 文档状态：技术栈无关设计草案
>
> 目标读者：前端开发者、后端开发者和接口设计人员
>
> 业务规模假设：同时在线不超过 1000 台，每台每秒约 1～2 条位置消息
>
> 相关文档：[无人机实时地图前端设计](./无人机实时地图前端设计.md)、[杭州 Cesium 三维示例需求规划](./cesium-hangzhou-requirements.md)

## 1. 文档目的

本文定义无人机实时地图所需的后端职责、数据模型、REST API、MQTT 协议、处理时序、可靠性和安全边界。

本文不绑定 Java、Node.js、Go、关系型数据库或时序数据库。具体技术选型可以变化，但对前端提供的行为和数据契约应保持稳定。

如果只熟悉前端，可以先记住后端在这个场景中解决四个问题：

1. 接收并校验真实无人机上报的数据。
2. 知道“现在有哪些无人机正在飞”。
3. 保存“一次飞行从起飞到当前或降落的完整轨迹”。
4. 通过 REST 提供基线数据，通过 MQTT 推送后续变化。

## 2. 为什么 REST 和 MQTT 都需要

MQTT 擅长把刚刚发生的变化快速推送给浏览器，但它不是当前完整状态的天然查询接口。用户打开页面之前已经发生的起飞事件，浏览器不一定能收到。

REST 和 MQTT 的分工如下：

| 通道 | 适合的内容 | 在本需求中的用途 |
| --- | --- | --- |
| REST | 查询一个确定时刻的完整结果 | 在线无人机快照、历史轨迹、设备点位、MQTT 临时凭证 |
| MQTT | 持续推送后续增量变化 | 位置更新、飞行状态变化、降落事件 |

因此采用“HTTP 快照 + MQTT 增量”模型：

```text
页面打开
  -> 建立 MQTT 订阅并暂存消息
  -> 请求 REST 在线快照
  -> 使用快照建立基线
  -> 重放较新的暂存消息
  -> 持续消费 MQTT 增量
```

这样既能快速看到实时变化，也能在首次进入或断线重连后恢复为权威状态。

## 3. 后端服务组成

逻辑上建议划分为以下能力。它们第一版可以部署在同一个应用中，不要求立即拆成微服务。

### 3.1 遥测接入

负责接收无人机、无人机平台或上游网关发送的数据：

- 校验无人机 ID、航次 ID、时间、序号和坐标。
- 统一经纬度、速度、高度和角度单位。
- 将不同厂商协议转换为内部统一模型。
- 拒绝非法、重复或明显过期的数据。

### 3.2 实时状态

负责维护每架无人机当前最新状态：

- 当前航次。
- 最新位置和姿态。
- 最新事件时间和序号。
- 飞行、降落或离线状态。
- 最近一次有效遥测时间。

这部分可以使用内存加持久化、分布式缓存或数据库实现，但服务重启后必须能够恢复或重新构建。

### 3.3 航次与轨迹

负责保存一次飞行任务：

- 起飞时创建或确认 `Flight`。
- 飞行中持续写入 `DroneTrackPoint`。
- 降落时结束当前航次。
- 按 `flightId` 返回有序轨迹。

轨迹属于历史事实，不能只保存在 MQTT 或进程内存中。

### 3.4 实时发布

负责将标准化后的增量事件发布到 MQTT Broker：

- 每架无人机使用稳定 Topic。
- 浏览器使用通配符订阅授权范围内的无人机。
- 支持 QoS 1，允许重复投递，由消费者按事件 ID 和序号去重。
- 不使用 retained 消息承担在线快照职责。

### 3.5 REST 查询

至少提供：

- MQTT 短期连接凭证。
- 当前在线无人机快照。
- 指定航次的历史轨迹。
- 地图设备点位。

## 4. 核心数据模型

以下字段表达业务含义，不代表必须使用同名数据库表。

### 4.1 无人机 Drone

```ts
type Drone = {
  droneId: string;
  name: string;
  model?: string;
  organizationId: string;
  enabled: boolean;
};
```

`Drone` 是设备主数据，不保存每秒变化的位置。

### 4.2 航次 Flight

```ts
type Flight = {
  flightId: string;
  droneId: string;
  status: "flying" | "landed" | "aborted";
  takeoffAt: string;
  landedAt?: string;
  takeoffPosition: GeoPosition;
  lastSequence: number;
};
```

一次重新起飞必须产生新的 `flightId`。不能只用 `droneId` 标识轨迹，否则多次飞行的数据会混到一起。

### 4.3 轨迹点 DroneTrackPoint

```ts
type DroneTrackPoint = {
  flightId: string;
  droneId: string;
  sequence: number;
  occurredAt: string;
  position: GeoPosition;
  speedMetersPerSecond?: number;
  headingDegrees?: number;
  pitchDegrees?: number;
  rollDegrees?: number;
};
```

`flightId + sequence` 应具有唯一性，用于幂等写入和排序。

### 4.4 统一位置 GeoPosition

```ts
type GeoPosition = {
  longitudeDegrees: number;
  latitudeDegrees: number;
  heightMeters: number;
  coordinateSystem: "WGS84";
  heightReference: "ELLIPSOID";
};
```

约束：

- 经度范围为 `[-180, 180]`。
- 纬度范围为 `[-90, 90]`。
- 角度单位为度，高度和速度单位分别为米、米/秒。
- 对外地图坐标统一为 WGS84。
- `heightMeters` 明确为椭球高，前端可直接传给 Cesium `Cartesian3.fromDegrees()`。

真实设备常见海拔高、离地高或厂商私有高度。接入层必须根据数据来源进行转换；不能只返回一个没有高度基准说明的 `altitude`。

### 4.5 当前状态 ActiveDroneState

```ts
type ActiveDroneState = {
  droneId: string;
  flightId: string;
  name: string;
  status: "flying" | "offline";
  position: GeoPosition;
  occurredAt: string;
  sequence: number;
  speedMetersPerSecond?: number;
  headingDegrees?: number;
};
```

已降落无人机不出现在活动快照中。`offline` 表示航次尚未确认结束但遥测暂时中断，不能等同于 `landed`。

### 4.6 地图设备 MapDevice

```ts
type MapDevice = {
  deviceId: string;
  type: "camera" | "sensor" | "station" | "droneBase";
  name: string;
  status: "online" | "offline" | "warning" | "maintenance";
  position: GeoPosition;
  updatedAt: string;
  properties: Record<string, unknown>;
};
```

`properties` 只能放经过权限过滤、确实允许前端展示的扩展字段，不能直接序列化整个数据库对象。

## 5. 前后端接口契约

### 5.1 通用 REST 响应

沿用当前前端项目的统一响应结构：

```ts
type ApiResponse<T> = {
  code: number;
  message: string;
  data: T;
};
```

约定：

- `code = 0` 表示业务成功。
- HTTP 状态码仍用于表达认证失败、权限不足、参数错误和服务异常。
- 时间统一使用带 `Z` 的 UTC ISO 8601，例如 `2026-09-07T08:30:15.123Z`。
- 所有 ID 在 JSON 中使用字符串，避免数据库长整数在 JavaScript 中丢失精度。

### 5.2 MQTT 会话接口

```http
POST /api/map/mqtt/session
Authorization: Bearer <access-token>
```

响应示例：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "wssUrl": "wss://mqtt.example.com/mqtt",
    "clientId": "web-user-42-b8f3",
    "username": "temporary-user",
    "password": "short-lived-secret",
    "expiresAt": "2026-09-07T09:00:00.000Z",
    "topicFilters": ["map/v1/drones/events/+"]
  }
}
```

设计要求：

- 凭证必须短期有效，且只允许连接指定 Broker、订阅指定 Topic。
- `clientId` 应避免同一用户多个页面互相踢下线。
- 接口根据当前用户的数据权限生成 Topic 范围。
- 响应禁止被共享缓存，服务端日志不得记录 `password`。

### 5.3 在线无人机快照

```http
GET /api/map/drones/active
Authorization: Bearer <access-token>
```

响应示例：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "asOf": "2026-09-07T08:30:15.123Z",
    "drones": [
      {
        "droneId": "drone-001",
        "flightId": "flight-20260907-001",
        "name": "巡检无人机 001",
        "status": "flying",
        "position": {
          "longitudeDegrees": 120.1551,
          "latitudeDegrees": 30.2741,
          "heightMeters": 132.5,
          "coordinateSystem": "WGS84",
          "heightReference": "ELLIPSOID"
        },
        "occurredAt": "2026-09-07T08:30:15.000Z",
        "sequence": 1862,
        "speedMetersPerSecond": 12.4,
        "headingDegrees": 83.2
      }
    ]
  }
}
```

快照必须来自一个语义一致的读取时刻。每架无人机携带当前航次最新序号，前端才能判断暂存 MQTT 事件是否更新。

### 5.4 航次历史轨迹

```http
GET /api/map/flights/{flightId}/track
Authorization: Bearer <access-token>
```

响应示例：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "flight": {
      "flightId": "flight-20260907-001",
      "droneId": "drone-001",
      "status": "flying",
      "takeoffAt": "2026-09-07T08:00:00.000Z",
      "takeoffPosition": {
        "longitudeDegrees": 120.1501,
        "latitudeDegrees": 30.2701,
        "heightMeters": 18.2,
        "coordinateSystem": "WGS84",
        "heightReference": "ELLIPSOID"
      },
      "lastSequence": 1862
    },
    "points": [
      {
        "sequence": 1,
        "occurredAt": "2026-09-07T08:00:00.000Z",
        "position": {
          "longitudeDegrees": 120.1501,
          "latitudeDegrees": 30.2701,
          "heightMeters": 18.2,
          "coordinateSystem": "WGS84",
          "heightReference": "ELLIPSOID"
        }
      }
    ],
    "sampled": false
  }
}
```

约定：

- `points` 按 `sequence` 升序返回。
- 正在飞行的航次也允许查询，`lastSequence` 表示本次响应覆盖到哪里。
- 轨迹过长时服务端可以按明确规则抽稀，并设置 `sampled = true`。
- 抽稀必须保留起飞点、最后点和关键状态变化点。
- 如果未来要求精确回放或轨迹分析，应增加分页或分段接口，不能依赖无限大的单次响应。

### 5.5 地图设备

```http
GET /api/map/devices?types=camera,sensor,station,droneBase
Authorization: Bearer <access-token>
```

响应示例：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "devices": [
      {
        "deviceId": "camera-001",
        "type": "camera",
        "name": "西湖巡检摄像头 001",
        "status": "online",
        "position": {
          "longitudeDegrees": 120.1425,
          "latitudeDegrees": 30.2525,
          "heightMeters": 26.0,
          "coordinateSystem": "WGS84",
          "heightReference": "ELLIPSOID"
        },
        "updatedAt": "2026-09-07T08:20:00.000Z",
        "properties": {
          "areaName": "西湖区"
        }
      }
    ]
  }
}
```

`types` 为空时的默认行为必须固定。建议返回用户有权查看的全部支持类型；无法识别的类型返回参数错误，不静默忽略。

## 6. MQTT 协议

### 6.1 Topic

单机事件 Topic：

```text
map/v1/drones/events/{droneId}
```

浏览器通常订阅：

```text
map/v1/drones/events/+
```

`v1` 是协议版本。未来出现不兼容字段变化时发布新版本，不直接破坏现有消费者。

### 6.2 消息结构

```ts
type DroneRealtimeEvent = {
  schemaVersion: 1;
  eventId: string;
  eventType: "drone.position" | "drone.status";
  droneId: string;
  flightId: string;
  sequence: number;
  occurredAt: string;
  status: "flying" | "landed" | "offline";
  position?: GeoPosition;
  speedMetersPerSecond?: number;
  headingDegrees?: number;
};
```

位置事件示例：

```json
{
  "schemaVersion": 1,
  "eventId": "evt-01J7K5R9M7",
  "eventType": "drone.position",
  "droneId": "drone-001",
  "flightId": "flight-20260907-001",
  "sequence": 1863,
  "occurredAt": "2026-09-07T08:30:15.500Z",
  "status": "flying",
  "position": {
    "longitudeDegrees": 120.1552,
    "latitudeDegrees": 30.2742,
    "heightMeters": 133.1,
    "coordinateSystem": "WGS84",
    "heightReference": "ELLIPSOID"
  },
  "speedMetersPerSecond": 12.7,
  "headingDegrees": 84.0
}
```

降落事件示例：

```json
{
  "schemaVersion": 1,
  "eventId": "evt-01J7K5S1AZ",
  "eventType": "drone.status",
  "droneId": "drone-001",
  "flightId": "flight-20260907-001",
  "sequence": 2140,
  "occurredAt": "2026-09-07T08:42:10.000Z",
  "status": "landed",
  "position": {
    "longitudeDegrees": 120.1502,
    "latitudeDegrees": 30.2702,
    "heightMeters": 18.3,
    "coordinateSystem": "WGS84",
    "heightReference": "ELLIPSOID"
  }
}
```

### 6.3 投递语义

- 使用 QoS 1，消息可能重复，消费者必须幂等。
- 默认 `retained = false`，在线基线由 HTTP 快照提供。
- `eventId` 全局唯一，用于日志追踪和短期去重。
- `sequence` 在单个 `flightId` 内严格递增，用于业务排序。
- Broker 的到达顺序不能代替业务序号。
- 同一无人机重新起飞后使用新 `flightId`，序号可以从 1 重新开始。

## 7. 服务端处理时序

### 7.1 位置事件

```text
接收厂商遥测
  -> 认证来源
  -> 校验字段和范围
  -> 转换坐标、单位和高度基准
  -> 根据 flightId + sequence 去重
  -> 持久化轨迹点
  -> 更新当前无人机状态
  -> 形成标准事件
  -> 发布 MQTT
```

不能先发布一条最终无法持久化的轨迹，再让历史接口永远查不到该点。生产环境建议使用事务消息或 Outbox 模式：业务数据和待发布事件先可靠写入，再由发布器重试发送 MQTT。

第一版如果暂不实现完整 Outbox，也必须记录发布失败并提供补偿重试，不能静默丢失。

### 7.2 起飞

起飞事件需要：

- 创建新的 `flightId`。
- 保存起飞时间和起飞点。
- 初始化当前状态和航次序号。
- 发布第一条 `flying` 状态或位置事件。
- 将无人机加入在线快照。

同一无人机只能有一个活动航次。重复的起飞通知必须幂等处理，不能生成多个并行航次。

### 7.3 降落

降落事件需要：

- 校验其航次仍是当前活动航次。
- 保存最终位置和降落时间。
- 将航次状态改为 `landed`。
- 从活动无人机状态中移除。
- 发布一次带最终序号的 `landed` 事件。

前端只有收到明确 `landed` 或在下一次权威快照中确认该航次已结束，才移除飞行图标。

### 7.4 遥测超时

长时间没有消息可能表示链路中断、设备离线或事故，不能自动当成正常降落。

建议流程：

1. 超过业务阈值后将状态改为 `offline`。
2. 发布 `offline` 状态事件并保留最后位置。
3. 后续恢复遥测时回到 `flying`。
4. 是否最终结束异常航次由独立业务规则或人工处理决定。

具体超时秒数属于业务配置，需要根据真实设备上报频率确定。

## 8. 快照和 MQTT 竞争处理

前端在请求快照时仍可能收到 MQTT 消息。例如快照中无人机序号为 100，而请求期间浏览器已经收到序号 101 和 102。

后端必须保证：

- 快照中的每架无人机包含 `flightId` 和最新 `sequence`。
- 轨迹接口包含本次响应的 `lastSequence`。
- MQTT 同一航次的序号单调递增。

前端据此只重放比快照更新的事件。仅提供一个 `asOf` 时间而不提供单机序号，在服务器时间、设备时间和网络延迟不一致时不够可靠。

## 9. 轨迹存储和查询注意事项

1000 台无人机每秒 2 个点，理论上每天可产生约 1.728 亿个轨迹点。即使真实在线量较低，也不能把轨迹当普通小表无限增长。

后端需要考虑：

- 按时间或航次分区。
- 使用 `flightId + sequence` 唯一约束实现幂等。
- 批量写入，但控制批次等待时间，避免实时延迟过大。
- 为航次查询建立合适索引。
- 规定原始轨迹保留期限和归档策略。
- 地图展示允许抽稀，审计或分析接口保留原始精度。
- 起飞点、降落点和告警点不能在抽稀时丢失。

前端地图需要的“好看的线”和业务需要的“完整原始记录”不是同一个查询目标。必要时应提供展示轨迹与原始轨迹两种读取方式。

## 10. 认证、授权和网络安全

### 10.1 REST

- 所有地图业务接口校验当前登录用户。
- 服务端根据组织、区域或设备权限过滤无人机和设备。
- 前端隐藏菜单不能代替服务端接口权限。
- 对非法 `flightId` 不泄露对象是否存在，可按权限策略统一返回无权访问或不存在。

### 10.2 MQTT

- 浏览器必须通过 `wss://` 连接。
- 禁止把 Broker 管理员账号、长期密码或服务端密钥写入前端环境变量。
- MQTT 会话凭证短期有效、最小权限、可撤销。
- Broker ACL 限制客户端只能订阅授权 Topic，不能发布无人机权威事件。
- 一个用户退出登录后，应使其 MQTT 凭证尽快失效。
- 限制单账号连接数、订阅数和消息速率，防止滥用。

### 10.3 数据安全

- 日志对 Token、MQTT 密码和敏感设备信息脱敏。
- 接口只返回地图展示需要的字段。
- 轨迹可能涉及敏感位置，需要明确保存期限、访问审计和导出权限。

## 11. 异常和恢复策略

| 异常 | 后端处理 | 前端可见结果 |
| --- | --- | --- |
| 重复遥测 | 按航次序号幂等忽略 | 不产生重复图标或轨迹点 |
| 乱序遥测 | 允许持久化后排序，当前状态只接受更新序号 | 地图不会倒退 |
| Broker 暂时不可用 | 事件进入重试或 Outbox | 页面可能短暂显示重连，恢复后快照校准 |
| 轨迹数据库写入失败 | 不确认成功，记录告警并重试 | 不发布无法查询的成功轨迹事件 |
| 当前状态缓存丢失 | 从活动航次和最新轨迹恢复 | 快照短暂不可用或降级 |
| 遥测中断 | 发布 `offline`，不发布 `landed` | 图标显示离线状态而不是消失 |
| 无法转换坐标 | 拒绝进入标准事件流并告警 | 前端不收到错误坐标 |
| MQTT 凭证过期 | 拒绝新连接，允许重新申请 | 前端重新获取凭证并校准快照 |

## 12. 性能和容量设计

当前基线为不超过 1000 台、每台每秒 1～2 条消息。后端容量验证至少覆盖：

- 峰值每秒约 2000 条遥测写入。
- 同等规模的状态更新和 MQTT 发布。
- 多个浏览器客户端同时订阅造成的扇出压力。
- 在线快照查询不能扫描全部历史轨迹。
- 单航次轨迹查询不能阻塞实时遥测接入。

优化优先级建议：

1. 先保证幂等、正确状态和可恢复。
2. 再对轨迹写入进行批处理和分区。
3. 将当前状态与历史轨迹分开存取。
4. 根据 Broker 和客户端数量评估 Topic 分片或网关聚合。
5. 不在没有压测证据时提前拆分大量微服务。

需要监控的指标：

- 遥测接收量、拒绝量和重复量。
- 从设备发生时间到 MQTT 发布的延迟。
- Broker 在线连接、订阅数、积压和发布失败。
- 轨迹写入耗时与失败率。
- 在线快照查询耗时和结果数量。
- 异常结束、长时间离线和序号跳变的航次数量。

## 13. 后端测试和验收

### 13.1 契约测试

- REST 响应符合统一 `ApiResponse<T>`。
- JSON 时间、ID、坐标单位和高度基准符合约定。
- MQTT Topic、协议版本、QoS 和消息字段符合文档。
- 未知协议版本和非法枚举被明确拒绝。

### 13.2 业务测试

- 起飞创建唯一活动航次并进入在线快照。
- 位置事件更新当前状态并写入轨迹。
- 重复序号不会产生重复轨迹点或重复业务变化。
- 旧序号不会覆盖当前最新位置。
- 降落结束航次、离开活动快照并发布 `landed`。
- 遥测超时只产生 `offline`，不会伪造降落。
- 同一无人机重新起飞使用新的航次 ID。

### 13.3 恢复测试

- MQTT 断开期间发生状态变化，重连后的 HTTP 快照能够恢复正确集合。
- 快照请求期间产生新事件，前端可以根据序号正确合并。
- Broker 发布失败后重试不会造成业务重复。
- 服务重启后可以恢复活动航次和最新状态。

### 13.4 权限测试

- 未登录用户不能获取 MQTT 凭证、快照和轨迹。
- 普通用户不能读取其他组织的无人机或设备。
- 修改前端 Topic 不能绕过 Broker ACL。
- 浏览器凭证不能向权威事件 Topic 发布消息。

### 13.5 容量验收

- 模拟 1000 台无人机、每台每秒 2 条遥测。
- 记录接收、持久化、状态更新和 MQTT 发布延迟。
- 验证持续运行时消息积压不会无限增长。
- 验证在线快照和轨迹查询不会明显影响遥测接入。
- 容量结论必须注明测试机器、持续时间、客户端数量和数据规模。

## 14. 推荐的后端实施顺序

1. 确认真实无人机上报协议、坐标系、高度基准和状态来源。
2. 建立 Drone、Flight、TrackPoint 和当前状态模型。
3. 实现本地模拟遥测接入及起飞、位置、降落状态机。
4. 实现在线快照和航次轨迹 REST 接口。
5. 定义 MQTT Topic 和消息契约，完成服务端发布。
6. 实现短期 MQTT 凭证和 Broker ACL。
7. 实现前端重连所需的快照校准流程。
8. 增加设备点位接口。
9. 补充幂等、乱序、离线、发布失败和服务重启测试。
10. 使用目标规模压测，再决定缓存、分区、批处理和部署拆分。

## 15. 实施前必须由业务或设备方确认

下面的信息不能由前端或后端开发者自行猜测：

1. 哪一个上游字段能唯一标识无人机。
2. 一次起飞和降落怎样产生、结束唯一航次。
3. 设备时间是否可信，序号由设备还是平台生成。
4. 原始坐标是 WGS84、GCJ-02 还是厂商局部坐标。
5. 高度是椭球高、海拔高、相对起飞点高度还是离地高度。
6. 多久没有遥测才视为离线，以及异常航次怎样结束。
7. 哪些用户可以查看哪些无人机、设备和历史轨迹。
8. 原始轨迹保存多久，是否允许抽稀、导出或跨组织查询。
9. 浏览器目标网络能否访问 MQTT `wss://` 地址。

这些问题未确认前可以使用模拟数据开发，但必须在联调前形成正式结论并更新接口契约。

## 16. 容易踩的后端坑

1. **只提供 MQTT，不提供快照**：页面首次进入和重连后无法知道完整在线集合。
2. **只用 droneId 保存轨迹**：同一无人机多次飞行会混成一条路线。
3. **没有业务序号**：消费者无法可靠处理重复和乱序消息。
4. **把离线当降落**：会产生错误航次和错误地图状态。
5. **高度没有基准**：前端即使收到数字也无法正确放置无人机。
6. **先发布、后持久化且没有补偿**：实时页面见过的轨迹可能永远无法从历史接口查到。
7. **使用长期 Broker 密码连接浏览器**：凭证会被任何访问页面的人获取。
8. **只做前端路由权限**：用户仍可直接调用接口或自行订阅 Topic。
9. **轨迹接口无限返回原始点**：长航次会造成数据库、网络和浏览器同时承压。
10. **过早拆微服务**：会先增加分布式一致性问题，应在边界清晰和压测后再拆分。
