# 单实例部署与备份恢复

本文对应阶段 7。先在本机完成生产构建和恢复演练，再按目标服务器修改路径、域名与证书。本项目使用一个后端进程和一份 SQLite 数据库。

## 一、请求和文件分别放在哪里

```text
浏览器 ── HTTPS ── Nginx
                    ├─ /、/assets/、/cesiumStatic/ → 前端 dist/
                    └─ /api/ → 127.0.0.1:3000 → Node.js → 持久目录/app.db
```

前端 `pnpm build` 生成静态文件；后端 `pnpm build` 生成 `dist/server.js`。二者各自的 `dist/` 不是同一个目录。

- 前端：发布整个 `dist/`，包含 Cesium 的 Workers、Assets、ThirdParty 和 Widgets，不能只上传 `index.html` 与 `assets/`。
- 后端：保留 `dist/`、`migrations/`、生产依赖、`package.json` 和锁文件。迁移文件按编号追加，已应用的文件不要改名或改写。
- 数据库：使用代码发布目录以外的持久目录，例如 `/srv/cesium-data/app.db`。更新代码时不替换这个目录。
- 备份：使用 Web 根目录以外的目录，例如 `/srv/cesium-backups/`，并另存一份到其他磁盘或机器。
- 配置：后端 `.env` 不提交、不发布为静态文件；前端 `VITE_` 变量会进入浏览器产物，不能存服务端秘密。

`vite.config.ts` 的 `server.proxy` 只负责开发代理。发布静态文件后，需要由 Nginx 转发 `/api`。无需为当前同源部署增加跨域配置。

## 二、首次安装和生产构建

统一使用符合两个项目要求的 Node.js >= 22.20.0。两仓库分别声明 pnpm 版本，由 Corepack 按各自的 `packageManager` 选择；首次安装需要能够访问包仓库。

前端在 `frontend_single` 分支执行：

```powershell
pnpm install --frozen-lockfile
pnpm lint
pnpm test
pnpm build
```

本分支 `.env.production` 默认 `VITE_BASE_PATH=/`，用于网站根目录部署。部署到子目录时，在构建前明确设置对应路径并重新构建。历史 Pages 工作流会显式覆盖此值；Pages 自身不能提供这个项目所需的 Node.js API。

前端 `.env.local` 可设置自己的天地图和 Cesium ion Token。缺少天地图 Key 的管理地图会回退到 OSM；外部地图、地形和影像仍取决于网络及服务授权。更新 `VITE_` 配置后需要重建前端。

后端在自己的仓库执行：

```powershell
pnpm install --frozen-lockfile
pnpm lint
pnpm typecheck
pnpm test
pnpm test:production
```

`pnpm test:production` 会先构建，再用临时数据库启动编译后的真实后端，执行迁移、初始化、四模块操作、重启、运行中备份及恢复核对。它不读取开发 `.env`，不修改开发数据库。

首次启动时，复制 `.env.example` 到 `.env`（已有配置时不要覆盖），填写：

```dotenv
HOST=127.0.0.1
PORT=3000
DATABASE_PATH=/srv/cesium-data/app.db
ADMIN_USERNAME=admin
ADMIN_PASSWORD=在本机填写自己的初始化密码
```

Windows 本机验证可使用 `DATABASE_PATH=data/app.db` 或自己的绝对路径。相对数据库路径始终以**后端项目根目录**为基准。管理员密码要求 15～128 个字符，不要直接使用文档中的占位文字。

构建后可完全通过 Node.js 运行维护命令和服务：

```powershell
node --env-file-if-exists=.env dist/scripts/migrate.js
node --env-file-if-exists=.env dist/scripts/seed.js
pnpm start
```

初始化成功后可移除配置中的 `ADMIN_PASSWORD`。再次运行初始化会跳过已有管理员，不重置密码。迁移必须在启动前显式执行，启动命令只检查结构是否就绪。

如果生产机器只安装生产依赖，源码命令 `pnpm db:migrate`、`pnpm db:backup` 等依赖的 `tsx` 不存在，应使用上面的编译产物命令。生产运行不需要 Vite、TypeScript 或 `tsx`。构建可以在另一台相同系统架构且符合环境要求的机器上完成。

## 三、数据库备份

后端新增 `src/databaseBackup.ts`，备份与恢复共用一致性复制和完整性检查，避免两个命令重复实现文件保护。命令入口在 `src/scripts/backup.ts` 和 `restore.ts`。没有增加 HTTP 备份接口。

在后端项目根目录执行，目标文件必须是一个**新文件名**：

```powershell
pnpm db:backup D:/cesium-backups/before-upgrade-20261107.db
```

只安装生产依赖时执行：

```powershell
node --env-file-if-exists=.env dist/scripts/backup.js /srv/cesium-backups/before-upgrade-20261107.db
```

执行顺序是：按 `DATABASE_PATH` 只读打开源库 → 排他创建目标 → SQLite `backup()` 生成一致性快照 → `integrity_check` 和 `foreign_key_check` → 输出成功路径。

此备份可在后端运行时执行，包含 WAL 中已经提交的数据。测试已验证保持源库连接且启用 WAL 时仍可恢复。不要通过直接复制运行中的 `app.db` 替代，也不要单独丢弃数据库旁的 `-wal`、`-shm` 或 `-journal` 文件。

命令拒绝覆盖已有文件，拒绝目标旁存在旧日志文件的情况；源文件不存在时直接失败，不创建空源库。失败产物只在确认由本次命令创建时清理。

备份包含账号密码哈希、会话摘要及业务数据。限制备份目录访问权限，不放到前端静态目录或 Git；Unix 新建备份文件权限为 `600`，Windows 还应依靠目录 ACL 限制访问。每次升级前备份，重要数据按需要定期备份；同一磁盘上的备份不能应对整盘损坏。

## 四、恢复演练

恢复前先停止后端，并暂停对外写入。恢复命令要求同时指定源备份和新的目标文件，**不会原地覆盖现有数据库，也不会自动切换服务配置**。

```powershell
pnpm db:restore D:/cesium-backups/before-upgrade-20261107.db D:/cesium-data/restored-20261107.db
```

只安装生产依赖时执行：

```powershell
node dist/scripts/restore.js /srv/cesium-backups/before-upgrade-20261107.db /srv/cesium-data/restored-20261107.db
```

恢复会检查完整性和外键，并清空**恢复库**中的 `sessions`，使所有用户重新登录；原库和备份文件中的会话不受影响。这样备份后已退出或被撤销的令牌不会因恢复而重新生效。密码与业务数据回到备份时的状态。

接着：

1. 将后端 `.env` 的 `DATABASE_PATH` 指向恢复后的新文件。若进程管理器设置了同名环境变量，也要同步修改，环境变量优先于 `.env`。
2. 使用与备份结构兼容的代码，运行迁移，再启动后端。不要重新初始化或重置账号来代替恢复核验。
3. 用备份时有效的密码重新登录，核对用户、避难场所、航线航点、重点单位共同中心和三层参数。
4. 检查分页和详情，再重启服务核对一次。确认成功后再开放写入，原库先保留用于排查。

恢复演练应使用临时文件和独立端口。只有备份成功还不够，必须证明恢复后能够登录并读取实际业务记录。若备份后重置过密码或权限，恢复也会回退这些变更，需要重新处理。

## 五、单实例 Nginx 配置示例

下面是 Linux 同源、根路径部署的示例。修改域名、证书和目录后，需要在目标服务器运行 `nginx -t`。本轮没有安装 Nginx 或签发证书，这份示例不代表服务器已部署。

```nginx
server {
    listen 80;
    server_name cesium.example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name cesium.example.com;
    ssl_certificate /etc/letsencrypt/live/cesium.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/cesium.example.com/privkey.pem;

    root /srv/cesium-frontend/dist;
    index index.html;
    include /etc/nginx/mime.types;
    default_type application/octet-stream;

    client_max_body_size 1m;
    error_page 413 = @too_large;
    location @too_large {
        default_type application/json;
        return 413 '{"code":41300,"message":"请求体不能超过 1 MB","data":null}';
    }

    location /api/ {
        # 末尾不加 /：保留完整 /api/...，与后端路由一致。
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_read_timeout 30s;
        add_header Cache-Control "no-store" always;
    }

    location = /index.html {
        add_header Cache-Control "no-cache" always;
    }

    location / {
        try_files $uri $uri/ =404;
    }
}
```

项目使用 Hash Router，页面路径在 `/#/...` 后面，浏览器刷新不要求 Nginx 将所有不存在的资源回退成 HTML。静态资源缺失应返回 404，以便发现发布不完整和公共路径错误。`mime.types` 对 JavaScript、CSS、WebAssembly 等资源的正确加载很重要。

后端保持 `HOST=127.0.0.1`，只由本机反向代理访问。当前 Express 没有启用 `trust proxy`，登录限流按代理连接来源共享；本阶段保持原有限流策略，多用户正式部署前应根据实际可信代理层级单独设计和验证，不能直接信任任意转发头。

## 六、进程托管和升级

开发时的 `pnpm dev`、前端 `pnpm preview` 都不作为正式生产托管方案。Linux 可用 systemd 管理单个 Node.js 后端，示例：

```ini
[Unit]
Description=React Cesium backend
After=network.target

[Service]
Type=simple
User=cesium
WorkingDirectory=/srv/cesium-server
EnvironmentFile=/srv/cesium-server/.env
ExecStart=/usr/bin/node /srv/cesium-server/dist/server.js
Restart=on-failure
TimeoutStopSec=15
UMask=0077

[Install]
WantedBy=multi-user.target
```

`/usr/bin/node` 必须改为实际 Node.js 的绝对路径；提前创建服务用户并授予持久目录读写权限，Nginx 不需要读写数据库。systemd 启动不继承交互终端中的 nvm 环境。不要为同一 SQLite 数据库同时启动多个后端副本。

升级顺序：

1. 在发布目录完成依赖安装、构建和本阶段检查，记录当前前后端版本。
2. 停止对外写入与后端，执行升级前备份，确认成功；保留旧代码和配置。
3. 更新前后端产物及后端迁移文件；使用新后端运行迁移。
4. 启动后端，检查 `/api/health`，再通过网站地址登录，核对四个模块和 Cesium 静态资源。
5. 验证成功后恢复访问。迁移失败时停止发布，不能绕过启动检查强行运行。

回退不能只切换旧代码：新迁移可能不兼容旧代码。需要按恢复流程，把升级前备份恢复到新文件，切换配置和对应旧代码，再核验。备份之后的写入不会自动合并回来。
