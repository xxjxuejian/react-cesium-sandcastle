# 航线管理接口

更新日期：2026-11-07。阶段 5 已接通真实 Node.js 后端与 SQLite，前端 `frontend_single` 分支不提供运行时 Mock。本说明以当前接口和代码为准；早期模拟实现可在历史提交 `7b8323f` 查阅。

## 启动与数据库升级

后端新增 `migrations/003_create_airlines.sql`，只建立 airlines 表，保留已有账号、会话与避难场所。本轮已在当前开发数据库执行迁移；其他环境先运行 `pnpm db:migrate`，再启动后端 `pnpm dev`。前端同样运行 `pnpm dev`，默认将 `/api` 代理到本机 3000 端口。新表不自动放入演示航线。

管理员登录或刷新恢复会话后，菜单增加“系统管理 → 航线管理”。普通用户不显示管理菜单，直接请求以下接口返回 403。

## 接口清单与响应

完整前缀为 `/api/system-management/airlines`。前端 API 封装位于 `src/api/airlineManagement.ts`，请求拦截器负责添加 `/api` 和 Bearer token。

| 方法 | 相对路径 | API 方法 | 成功响应 data |
| --- | --- | --- | --- |
| GET | 空路径 | `getAirlineList(params?, signal?)` | `{ list, total }` |
| GET | `/:id` | `getAirlineDetail(id, signal?)` | 完整航线 |
| POST | 空路径 | `createAirline(values)` | 创建后的完整航线 |
| PUT | `/:id` | `updateAirline(id, values)` | 更新后的完整航线 |
| DELETE | `/:id` | `deleteAirline(id)` | `true` |

五个接口均要求有效会话和管理员身份。原始响应为 `{ code, message, data }`，前端封装返回解包后的 data。成功 code 为 0；航线参数错误使用 HTTP 400、code 40003；不存在使用 HTTP 404、code 40403。无会话为 HTTP 401，无管理员权限为 HTTP 403。全局 JSON 解析、请求体大小及异常处理继续使用 40000、41300、50000 等业务码。失败时 data 为 null，message 指出字段或航点序号。

## 列表只返回摘要

查询参数为 name、page、pageSize。name 为最多 100 个字符的文本，去除首尾空格后忽略英文大小写匹配子串；省略或空白表示不筛选，百分号和下划线按普通字符匹配。page 默认 1，pageSize 默认 10，必须为正整数且单页不超过 100。

后端先筛选计数，再按更新时间倒序、编号升序稳定分页。超过末页返回空数组及筛选后的总数。每条摘要仅包含：

```text
{ id, name, waypointCount, length, speed, updatedAt }
```

SQL 本身不读取航点 JSON、备注和创建时间。查看或编辑时单独查询详情。

## 保存资料与校验

新增和更新共用以下结构；PUT 整体替换资料及航点数组：

```json
{
  "name": "滨江巡检航线",
  "speed": 5,
  "remark": "沿江巡检",
  "waypoints": [
    { "longitude": 120.2102, "latitude": 30.2074, "altitude": 0 },
    { "longitude": 120.2152, "latitude": 30.2094, "altitude": 80 }
  ]
}
```

- name 去除首尾空格后为 1～100 个字符，允许同名。
- speed 必须为大于 0 的有限数值，单位米/秒。
- remark 最多 2000 个字符；可以省略，省略时保存为空字符串；保留输入空格，不接受 null 等非文本值。
- waypoints 必须包含 2～1000 个完整航点。经纬度采用 WGS84 度数，经度范围 -180～180，纬度范围 -90～90。
- altitude 是相对统一地面零平面的高度，单位米，有限数值且大于等于 0。零高度合法，不叠加起飞点、海拔偏移或地形高度。
- 不把 null、字符串或缺失值转换成零坐标或零高度。相邻航点不能经度、纬度、高度三项完全相同；允许垂直升降、路径交叉、非相邻重复点及手动闭合。

详情在列表摘要基础上增加 remark、createdAt、waypoints。后端根据数组顺序生成从 1 开始的 order，根据数组长度生成 waypointCount，并独立计算 length。请求带来的编号、时间、长度、数量、序号以及未知字段均不能覆盖这些结果。

id 为服务器生成的 UUID。数据库内部时间为 UTC，接口使用北京时间 `YYYY-MM-DD HH:mm:ss`。更新保留 id 和 createdAt，只刷新 updatedAt。

## 长度与持久化

length 为相邻航点水平大圆距离之和，单位米，不含高度差，不自动连接终点和起点。后端使用 Haversine 算法和平均地球半径 6371008.8 米，限定中间浮点结果范围以避免 NaN。接口保留计算精度，页面负责展示时的格式化。

前端 `src/utils/airline.ts` 仅计算草稿预览长度；后端在自己的 service 中维护经过测试的实现，不导入前端仓库。航点存入 waypoints_json，摘要列与完整航点由同一条 INSERT 或 UPDATE 写入。单条 SQL 失败会整体回滚，不留下半份摘要或部分航点。

## 从页面入口阅读代码

1. 前端 `src/pages/system-management/airline-management/index.tsx` 请求列表摘要，查看、编辑时再请求详情。
2. `AirlineEditor.tsx` 用 Form 保存唯一一份草稿；地图点击、拖动、手动输入、排序和批量高度都更新该表单。
3. 前端 `constants.ts` 让名称、备注、手动添加、地图添加和保存校验使用一致上限；达到 1000 个航点会停止连续绘制。前端限制用于及时提示，后端仍独立校验。
4. 点击保存后通过既有 API 方法和 Vite 代理进入后端 `src/app.ts` 注册的 `src/modules/airlines/routes.ts`。
5. 路由先检查会话与管理员角色，再调用 `service.ts` 完成白名单校验、编号、长度计算及 SQL；`types.ts` 解释摘要与详情字段。
6. 保存成功返回列表并刷新；失败显示后端消息并保留草稿。结束绘制和取消编辑不会写数据库，放弃修改后恢复列表。只读查看不提供保存操作。

CesiumMap 继续管理 Viewer 的创建与销毁，AirlineMap 负责本页实体与鼠标事件的清理。本阶段沿用二维地图，不新增飞行执行、三维预览、告警或圈层约束。高度与重点单位防御圈仍采用同一零平面约定。
