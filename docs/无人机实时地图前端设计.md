# 无人机实时地图前端设计

> 文档状态：设计草案
>
> 目标读者：主要熟悉 React 前端、准备逐步接入 Cesium 和实时数据的开发者
>
> 技术基线：React 19、TypeScript、Zustand、CesiumJS 1.143、MQTT over WebSocket
>
> 相关文档：[Cesium 通用基础组件技术方案](./cesium-base-architecture.md)、[杭州 Cesium 三维示例需求规划](./cesium-hangzhou-requirements.md)、[无人机实时地图后端设计](./无人机实时地图后端设计.md)

## 1. 文档目的

本文只描述无人机实时地图的前端职责和实现思路，重点回答以下问题：

- 左侧实时列表和地图图标怎样共享同一份数据。
- MQTT 推送一架无人机的位置变化后，怎样只更新对应图标。
- 新无人机、降落无人机和乱序消息怎样处理。
- 进入详情页后，怎样合并历史轨迹和实时轨迹。
- 其他设备怎样按类别显示、隐藏和响应点击。
- 当前项目中的 `CesiumMap` 是否需要扩展。

本文不会规定后端使用 Java、Node.js 或哪一种数据库。REST API、MQTT Topic、网络报文和服务端状态规则统一由[后端设计文档](./无人机实时地图后端设计.md)定义。

## 2. 先理解前后端边界

前端的核心任务是“消费可信数据并正确展示”，不是替代后端判断真实世界状态。

| 内容 | 前端负责 | 后端负责 |
| --- | --- | --- |
| MQTT 连接 | 获取临时凭证、连接、订阅、重连 | 签发受限凭证、鉴权、发布消息 |
| 无人机状态 | 将状态映射到列表和地图表现 | 判断飞行、降落、离线并发布权威状态 |
| 实时位置 | 去重、忽略旧消息、批量更新 UI | 校验、标准化、排序并发布遥测数据 |
| 在线集合 | 使用 HTTP 快照校准本地 Store | 返回权威的当前在线快照 |
| 历史轨迹 | 请求、合并、绘制 | 持久化并按航次返回有序轨迹 |
| 坐标 | 转换为 Cesium `Cartesian3` | 输出明确的 WGS84 和高度基准 |
| 设备点位 | 图层显隐、点击弹窗 | 返回设备资料和可见范围内的数据 |

需要特别注意：浏览器收到的 MQTT 消息可能重复、延迟或乱序。前端需要防御这些情况，但不能自行推断“长时间没消息就代表已经降落”。

## 3. 当前 CesiumMap 是否适用

当前 `src/components/CesiumMap/` 可以直接作为业务地图底座，不需要把 MQTT、无人机或设备能力继续塞进基础组件。

现有职责保持不变：

- `CesiumMap`：创建和销毁 `Viewer`，处理基础错误和容器尺寸变化。
- `useCesium()`：让后代组件取得当前已经就绪的 `Viewer`。
- `useCesiumEffect()`：创建 Cesium 资源，并在依赖变化或卸载时清理资源。
- 页面业务组件：管理 Entity、DataSource、轨迹、点击事件和业务错误。

继续遵守以下边界：

- 不把 `Viewer` 放进 Zustand。
- 不创建模块级的全局 `Viewer`。
- 概览页和详情页各自创建 Viewer，切换路由时允许销毁旧 Viewer。
- `CesiumMap2` 只作为学习对照，不在正式业务中导入。
- 第一版不增加图层注册中心、Cesium 事件总线或跨路由地图保活。

设计原因是 Viewer 包含 DOM、WebGL 和大量可变状态，而无人机、轨迹和设备属于可以脱离 Viewer 存在的业务数据。二者生命周期不同，不应该放在同一个全局 Store 中。

## 4. 前端整体结构

建议将未来代码按下面的职责组织。这里表达的是边界，不要求一开始就创建所有文件。

```text
src/features/drone-map/
├─ api/                    # 在线快照、轨迹、设备和 MQTT 凭证请求
├─ realtime/               # MQTT 连接、订阅、报文解析和批处理
├─ store/                  # 无人机业务状态，不保存 Viewer
├─ layers/                 # DroneLayer、DeviceLayer、FlightTrackLayer
├─ interaction/            # 统一地图点击处理
├─ components/             # 左侧列表、图层面板、设备弹窗
├─ types.ts                # 前端内部领域类型
└─ adapters.ts             # 后端 DTO 到前端领域对象的转换
```

整体数据流如下：

```text
REST 在线快照 ─┐
               ├─> 数据适配器 ─> Drone Store ─┬─> 左侧实时列表
MQTT 增量事件 ─┘                               └─> DroneLayer ─> Cesium Entity

REST 历史轨迹 ─┐
               ├─> 轨迹合并器 ─> FlightTrackLayer ─> 起飞点 + Polyline
MQTT 当前航次 ─┘

REST 设备接口 ─> Device Store/页面状态 ─> 分类 DataSource ─> 图层控制和设备弹窗
```

最重要的原则是：列表和地图使用同一个无人机 Store，不允许各自维护一份无人机数组。

## 5. 前端内部数据模型

网络报文以[后端设计文档的接口契约](./无人机实时地图后端设计.md#5-前后端接口契约)为准。前端收到数据后，先转换为下面的内部领域类型，再交给 Store 和 Cesium。

```ts
type DroneDisplayStatus = "flying" | "offline";

type DronePosition = {
  longitude: number;
  latitude: number;
  height: number;
};

type ActiveDrone = {
  droneId: string;
  flightId: string;
  name: string;
  status: DroneDisplayStatus;
  position: DronePosition;
  occurredAt: string;
  sequence: number;
  speed?: number;
  heading?: number;
};

type FlightTrackPoint = DronePosition & {
  occurredAt: string;
  sequence: number;
};

type MapDeviceType = "camera" | "sensor" | "station" | "droneBase";

type MapDevice = {
  deviceId: string;
  type: MapDeviceType;
  name: string;
  status: "online" | "offline" | "warning" | "maintenance";
  position: DronePosition;
  updatedAt: string;
};
```

这不是后端 DTO 的复制。适配器应负责：

- 检查必填字段和数值范围。
- 将后端坐标对象转换为页面统一的 `position`。
- 将无法识别的状态归入错误处理，而不是强制断言类型。
- 将时间统一保留为 UTC ISO 8601 字符串，需要比较时转换为时间值。
- 隔离将来后端增加字段、修改嵌套层级带来的影响。

## 6. 无人机 Store 设计

### 6.1 Store 保存什么

建议按 ID 保存无人机，而不是只保存数组：

```ts
type DroneState = {
  activeById: Map<string, ActiveDrone>;
  lastSequenceByFlight: Map<string, number>;
  connectionStatus: "idle" | "connecting" | "connected" | "reconnecting" | "error";
  snapshotStatus: "idle" | "loading" | "ready" | "error";
};
```

`activeById` 让新增、查找、更新和删除都可以按 ID 完成。`lastSequenceByFlight` 即使在无人机降落并从活动集合删除后也需要暂时保留，用来阻止迟到的旧消息把无人机重新加回来。

Store 不保存以下内容：

- `Viewer`、Entity、DataSource 等 Cesium 对象。
- MQTT Client 实例。
- React 弹窗节点或 Cesium 点击事件对象。
- 可以从已有状态直接计算出来的重复数组。

### 6.2 增量事件处理规则

每批事件按下面的顺序处理：

1. 检查 `droneId`、`flightId`、`sequence` 和状态是否合法。
2. 使用 `flightId + sequence` 判断消息是否比本地记录更新。
3. 旧消息和重复消息直接忽略。
4. `flying` 事件不存在对应无人机时新增，存在时更新位置和业务字段。
5. `offline` 只改变显示状态，不伪装成降落。
6. `landed` 从 `activeById` 删除，但保留最后序号作为短期墓碑记录。
7. 一批处理完成后只提交一次 Zustand 状态。

墓碑记录不需要永久保存。完成一次新的 HTTP 在线快照校准，且确认不存在旧航次消息后即可清理。

使用 `Map` 时不要直接在旧状态对象上调用 `set()` 或 `delete()` 后原样返回。每个批次应复制一次 `Map`，在副本上完成本批修改后再提交新引用，否则 Zustand 订阅者可能无法感知变化。

### 6.3 为什么需要批处理

1000 台无人机、每台每秒 2 条消息意味着峰值约 2000 条消息/秒。如果每条消息都执行一次 Zustand 更新、React 渲染和 Cesium 请求渲染，浏览器会把大量时间花在调度上。

第一版建议在 MQTT 适配层暂存消息，每约 100ms 合并一次：

- 同一架无人机在一个批次中只保留序号最新的事件。
- Store 每批只更新一次。
- Cesium 每批只调用一次 `scene.requestRender()`。
- 左侧列表通过选择器和稳定的行 key 减少无关行重渲染。

100ms 是初始值，不是永久标准。后续应根据真实消息量和交互体验调整。

## 7. MQTT 连接和快照校准

### 7.1 首次进入页面

仅订阅 MQTT 无法知道订阅前已经有哪些无人机，因此必须使用 HTTP 在线快照进行校准。

推荐时序：

1. 调用 MQTT 会话接口取得短期连接凭证。
2. 建立 `wss://` 连接并订阅无人机事件 Topic。
3. 暂存订阅后收到的 MQTT 消息，先不覆盖 Store。
4. 请求 HTTP 在线无人机快照。
5. 使用快照替换 `activeById`。
6. 按航次序号重放暂存的 MQTT 消息。
7. 切换到正常增量处理状态。

先订阅再请求快照，是为了避免 HTTP 请求期间出现一段消息空窗。快照和暂存消息仍可能包含相同数据，所以序号去重不可省略。

### 7.2 断线重连

MQTT 自动重连成功不代表本地状态仍然完整。断线期间可能发生起飞、移动或降落，因此重连后要重新执行快照校准。

重连过程中：

- 列表和地图可以保留最后状态，但界面要显示“连接恢复中”。
- 不应立即清空全部无人机，否则短暂网络波动会造成地图闪烁。
- 校准成功后再一次性修正新增、位置变化和已消失对象。
- 多次重连只能存在一个有效校准请求，旧请求需要取消或忽略结果。

### 7.3 React StrictMode

开发环境的 StrictMode 会执行额外的 Effect 建立和清理检查。MQTT 连接层必须满足：

- `connect()` 重复调用不会创建无法管理的并行连接。
- `disconnect()` 和取消订阅可以安全重复执行。
- 页面卸载后，旧连接回调不能继续更新 Store。
- 重连定时器、批处理定时器和待处理 Promise 都有清理路径。

## 8. 无人机 Cesium 图层

### 8.1 图层生命周期

`DroneLayer` 是一个不渲染 DOM 的场景组件。它只在挂载时创建一个 `CustomDataSource("drones")`，并在卸载时移除。

```text
DroneLayer 挂载
  -> 创建 CustomDataSource
  -> 加入 viewer.dataSources
  -> 订阅 Drone Store
  -> 增量同步 Entity

DroneLayer 卸载
  -> 取消 Store 订阅
  -> 从 Viewer 移除 DataSource
```

不要把不断变化的无人机数组放到 `useCesiumEffect` 的依赖列表中。否则每次 MQTT 更新都可能触发 cleanup，导致整层无人机被删除再重建。

### 8.2 Entity 增量同步

当前规模为千台以内、每台每秒 1～2 次，第一版优先使用 Entity：

- Entity ID 使用稳定格式，例如 `drone:${droneId}`。
- 新无人机调用一次 `entities.add()`。
- 位置变化只更新已有 Entity 的 `position`。
- 状态样式变化只修改 Billboard、Label 等属性。
- 降落时按 ID 移除 Entity。
- 批量新增或删除时使用 `suspendEvents()` / `resumeEvents()`。

每个 Entity 应携带最小拾取元数据，例如对象类别和业务 ID。完整详情继续从 Store 或接口读取，不要把整个业务对象复制进 Entity。

### 8.3 按需渲染

当前 `CesiumMap` 默认配置包含：

```ts
requestRenderMode: true,
maximumRenderTimeChange: Number.POSITIVE_INFINITY,
```

这适合静止地图降低 CPU/GPU 占用，但业务层更新 Entity 或轨迹后必须主动调用：

```ts
viewer.scene.requestRender();
```

调用频率以“每批一次”为准，不能在循环更新每个 Entity 时分别调用。

### 8.4 何时考虑 Primitive

第一版不要提前使用 `BillboardCollection` 或其他 Primitive 重写图层。只有压力测试证明 Entity 已成为瓶颈时，再只替换 `DroneLayer` 内部渲染实现，页面、Store 和网络层保持不变。

可能触发迁移的信号包括：

- 可见无人机明显超过当前千台规模。
- 提高频率后长时间低于项目性能目标。
- Entity 属性更新和 Visualizer 成为主要 CPU 热点。
- 显存或垃圾回收频率持续增长。

## 9. 无人机详情和实时轨迹

### 9.1 进入详情页

点击地图无人机后，根据 Entity 中的 `droneId` 和 `flightId` 进入详情路由。详情页创建新的 `CesiumMap`，不尝试搬运概览页 Viewer。

详情页应并行开始两件事：

1. 请求当前 `flightId` 的历史轨迹。
2. 订阅并暂存该航次的新 MQTT 消息。

历史请求完成后，以 `sequence` 为主键进行合并、排序和去重，然后进入正常追加状态。这样可以避免历史接口请求期间丢失新轨迹点。

### 9.2 第一版轨迹表现

第一版实时监控只需要：

- 一个起飞点 Entity。
- 一个代表当前无人机位置的 Billboard Entity。
- 一个包含已发生轨迹的 Polyline Entity。

每批新轨迹点到达后，更新 Billboard 位置并向 Polyline 追加去重后的坐标，然后调用一次 `requestRender()`。

此方案不包含历史回放、暂停、倍速或平滑插值。如果后续增加回放功能，再独立引入 `SampledPositionProperty`、Clock 和 Path，避免一开始把实时监控与时间播放混成一个复杂状态机。

### 9.3 降落后的表现

详情页收到 `landed` 后：

- 停止向当前航次追加实时点。
- 移除移动中的无人机图标。
- 保留起飞点和已经形成的完整轨迹。
- 页面状态显示“已降落”，不自动跳回概览页。

## 10. 其他设备和图层控制

摄像头、传感器、基站和无人机起降点等数据变化频率较低，可以按设备类型各创建一个 `CustomDataSource`：

```text
camera      -> CustomDataSource("devices:camera")
sensor      -> CustomDataSource("devices:sensor")
station     -> CustomDataSource("devices:station")
droneBase   -> CustomDataSource("devices:droneBase")
```

图层面板使用 React 本地状态保存各类别是否可见，并直接设置对应 `dataSource.show`。第一版不需要通用图层注册中心。

设备点位加载失败时只标记对应设备层失败，不能让整个 Viewer 或无人机层停止工作。

## 11. 统一点击交互

同一个页面只注册一个左键点击入口：

1. 使用 `scene.pick()` 获取最上层对象。
2. 从 Entity 元数据判断是无人机还是哪类设备。
3. 无人机触发 React Router 导航。
4. 设备把 `deviceId` 写入 React 页面状态并打开 Ant Design 弹窗。
5. 点击空白区域时关闭当前设备弹窗或取消选择。

不要让 `DroneLayer`、`CameraLayer`、`SensorLayer` 分别覆盖同一个 `LEFT_CLICK`。统一入口可以避免处理器相互覆盖，也便于以后增加区域、建筑等对象。

点击处理器由创建它的场景组件负责移除。第一版只处理点击，不增加高频鼠标移动拾取；如果以后增加悬停，需要节流并优先评估 `pickAsync()`。

## 12. 页面状态和 Cesium 状态怎样分工

| 状态 | 建议位置 | 原因 |
| --- | --- | --- |
| 在线无人机数据 | Zustand 业务 Store | 列表和地图共同使用 |
| MQTT 连接状态 | Zustand 业务 Store | 页面需要显示连接提示 |
| 当前设备弹窗 | 页面 `useState` | 只影响当前页面 UI |
| 设备图层开关 | 页面 `useState` | 离开页面后可以恢复默认值 |
| Viewer | Cesium Context | 与地图 DOM 生命周期绑定 |
| DataSource、Entity | 场景组件 Ref/闭包 | 属于命令式 Cesium 资源 |
| 详情页轨迹 | 详情页 Store 或 Hook | 只属于当前航次页面 |

不要为了减少 Props 而把所有状态都放进全局 Store。只有确实需要跨组件共享或跨请求协调的数据才进入 Zustand。

## 13. 错误与用户提示

页面至少要区分下面几类状态：

- Cesium Viewer 初始化失败。
- MQTT 正在连接、已连接、正在重连或连接失败。
- HTTP 在线快照加载失败。
- 历史轨迹加载失败。
- 单类设备图层加载失败。
- 收到无法解析的实时消息。

处理原则：

- Viewer 基础错误由 `CesiumMap` 展示。
- MQTT 断线不立即清空最后画面，但要显示数据可能已过期。
- 快照校准失败时不能假装当前列表完整，应保留明确的“未完成校准”状态。
- 单个设备层失败不能阻塞无人机图层。
- 错误日志不要打印 MQTT 密码、Token 或完整用户凭证。

## 14. 建议的前端实施顺序

为了便于学习和排查，每一步只增加一个可观察能力：

1. 使用本地模拟数组实现左侧列表和 `DroneLayer`，验证稳定 ID 的新增、更新、删除。
2. 增加 Zustand Store，让列表和地图改为读取同一个数据源。
3. 使用模拟定时器产生单机增量事件，验证批处理、乱序和降落。
4. 接入 HTTP 在线快照，完成首次进入的数据校准。
5. 接入 MQTT 临时凭证、连接、订阅和重连。
6. 增加无人机点击和详情路由。
7. 接入历史轨迹，并与详情页 MQTT 增量合并。
8. 增加设备 DataSource、图层开关和设备弹窗。
9. 使用目标规模执行性能、生命周期和异常恢复验证。

不建议第一步就同时接入真实 MQTT、轨迹、所有设备和完整视觉设计，否则出现问题时很难判断是数据、React 还是 Cesium 导致。

## 15. 前端测试和验收

### 15.1 可自动化测试

- 新无人机事件加入活动集合。
- 新位置只更新对应无人机。
- 重复或旧序号事件被忽略。
- 降落事件移除无人机，迟到旧消息不能将其恢复。
- HTTP 快照和暂存 MQTT 消息合并后结果正确。
- 历史轨迹和实时点按序号排序、去重。
- DTO 适配器拒绝非法经纬度、空 ID 和未知协议版本。
- 图层同步不会为位置变化重复创建 Entity。

## 16. 实施时容易踩的坑

1. **把 MQTT 原始 JSON 直接传给组件**：会让协议变化影响所有页面，应先经过适配器。
2. **列表和地图各维护一份数组**：迟早会出现数量和状态不一致。
3. **每条消息都 setState**：高频更新会造成大量 React 调度。
4. **把实时数组放进 `useCesiumEffect` 依赖**：会反复清理并重建图层。
5. **循环中多次 `requestRender()`**：应在一个批次处理结束后调用一次。
6. **用消息到达顺序代表真实顺序**：MQTT QoS 1 仍可能重复，网络也可能导致乱序。
7. **失联等同于降落**：这是错误业务判断，降落必须来自后端权威状态。
8. **忽略高度基准**：同样的高度数字可能代表椭球高、海拔高或离地高，会导致模型悬空或钻地。
9. **每个图层注册一个点击处理器**：容易互相覆盖或重复响应，应统一拾取。
10. **为了详情页保留整个 Viewer**：当前需求通过重新创建 Viewer 和重新加载业务数据即可完成，先不要增加跨路由保活复杂度。
11. **直接修改 Zustand 中旧的 Map**：引用没有变化时，React 订阅组件可能不重新渲染；应按批次创建新 Map。
